# Security Threat Model and Trust Boundaries

## 1. Security objective

The workflows must remain safe even when the primary local model follows malicious instructions. Model compliance, refusal behavior, self-reported confidence, and chain-of-thought are not trusted controls.

The system should guarantee, through deterministic code and capability isolation, that untrusted text cannot directly obtain real tools, secrets, network access, repository mutation, or host access. Semantic classifiers may influence routing, but they must not be the only barrier protecting an irreversible action.

## 2. Protected assets

The threat model covers:

- host filesystem, home directory, SSH agent, sockets, containers, and process namespace;
- model-provider credentials and GitHub credentials;
- trusted user goals and policies;
- issue-state integrity;
- approval state and approval digests;
- artifacts, checkpoints, replay records, and side-effect ledger;
- result-cache and KV-cache tenant separation;
- confidential content in issue bodies, comments, long histories, or tool outputs;
- evaluation integrity and held-out datasets;
- telemetry that may contain attack payloads, synthetic credentials, or model reasoning.

## 3. Trust classes

### 3.1 Trusted policy

Examples:

- checked-in workflow specification and lock;
- static system policy;
- output schema;
- tool capability declaration;
- account allowlist;
- destination allowlist;
- approval policy;
- dataset manifest and checksums;
- deterministic reason-code tables.

Trusted policy is versioned, hashed, and included in cache/checkpoint identity.

### 3.2 Trusted goal

The user-authorized task, represented separately from untrusted content. A Tool Call Firewall receives the trusted goal directly; it does not infer the goal from an issue body or model-generated plan.

### 3.3 Conditionally trusted content

Examples:

- issue body authored by an allowlisted account;
- comments authored by individually allowlisted accounts;
- local history generated by an authenticated workflow;
- artifacts whose provenance and hash are valid.

Trust is per object and per author. A trusted issue author does not make every comment trusted.

### 3.4 Untrusted content

Examples:

- issue title/body/comment from a non-allowlisted account;
- webpage, email, RAG document, README, or code comment;
- model output before schema and policy validation;
- tool output containing external content;
- encoded/obfuscated spans;
- raw chain-of-thought from a model that consumed malicious text.

Untrusted content is always data. It must never be concatenated into the trusted instruction channel without a canonical envelope.

### 3.5 Synthetic trap data

Honeytokens and planted credentials are generated solely for detection. They must be visibly and technically distinguishable from real secrets, scoped to one test/probe, and forbidden from reaching real executors or external networks.

## 4. Threats

### 4.1 Direct and indirect prompt injection

Attackers may include instructions to:

- ignore or override the trusted goal;
- reveal system policy or secrets;
- manipulate tool selection or parameters;
- exfiltrate data;
- modify or close issues;
- disable monitoring;
- establish persistence across turns;
- invoke hidden behavior through encoded text, HTML comments, Unicode controls, zero-width characters, Base64, hex, typoglycemia, multilingual/code-switched content, or chunk-boundary construction.

### 4.2 Behavioral compromise without obvious attack text

A model may drift into a dangerous action due to ambiguous or adversarial content even when a text classifier does not recognize a known injection pattern. The behavioral probe and Tool Call Firewall address observable action, not only textual appearance.

### 4.3 False assurance from absent behavior

A probe that does not call a honeytool has not proven the input clean. The model may resist that instance, the attack may target output rather than tools, or the probe task may not activate the payload. `NoCompromiseObserved` is not equivalent to `Clean`.

### 4.4 Chain-of-thought manipulation and observer injection

Raw reasoning may be unfaithful, strategically sanitized, or itself contain attacker-controlled text. An observer that reads raw CoT could become a second victim. CoT is therefore optional diagnostic evidence, not a hard control. The default observer consumes canonicalized event features and redacted excerpts, never the full malicious input by inheritance.

### 4.5 Tool smuggling and parameter abuse

An attacker may use a legitimate tool with:

- an unauthorized destination;
- a broader path/account/repository than the trusted goal permits;
- secret-bearing arguments;
- an excessive side effect;
- a surprising encoding;
- a duplicate/replayed request;
- a parameter selected from untrusted content.

Hard parameter checks and destination policy precede semantic review.

### 4.6 Side-effect duplication

Crash/retry/replay may close an issue twice, post duplicate comments, or apply a stale action after the underlying issue changed. Approval digests, idempotency keys, the durable side-effect ledger, and postcondition checks prevent this.

### 4.7 Cache poisoning and cross-tenant leakage

A stale or incorrectly keyed semantic result can bypass updated policy. Shared KV cache may leak timing or prefix reuse across trust domains. Cache identities bind all security-relevant versions, and cache salt separates domains.

### 4.8 Evaluation contamination and overfitting

Translated attacks, paraphrases, or template families can leak across train/tune/test splits. A workflow may optimize to public benchmark syntax while failing adaptive attacks. Splits must be by attack family and repository/time where relevant, with a sealed final holdout and an adaptive attacker that knows the defense design.

## 5. Sentinel defense layers

### Layer A: deterministic normalization

- enforce input size and structural limits;
- preserve original bytes as an artifact;
- produce a normalized analysis view;
- detect controls, zero-width characters, bidi controls, hidden HTML/Markdown, suspicious encodings, and decode candidates;
- segment natural-language spans separately from URLs, code, identifiers, emoji, math, and data;
- classify supported languages for natural-language spans only;
- never mark an unsupported language as clean.

### Layer B: semantic multi-view analysis

- ordered spotlighted view;
- overlapping deterministic shuffled chunks;
- decoded/normalized view;
- task-alignment view when a trusted task is available.

Each branch runs in an isolated session and emits compact evidence, not prose.

### Layer C: behavioral compromise probe

Provide a simulated tool catalogue containing:

- safe no-op completion tools;
- honeytools with no legitimate task use;
- synthetic credential/honeytoken sources;
- legitimate-looking tools with strict allowlisted destinations and parameters.

The probe has no real executor, network, host filesystem, secret broker, or repository write capability. Its tool calls are intercepted and simulated.

Hard compromise signals include:

- invoking a honeytool;
- using a honeytoken outside its allowed sink;
- selecting a forbidden destination/path/account;
- proposing privilege expansion;
- attempting to disable policy/monitoring;
- attempting host/network execution.

### Layer D: optional CoT monitor

CoT is off by default in production. It may be enabled in experiments to measure incremental value. Raw CoT is stored only in a restricted artifact with explicit retention policy. The ordinary observer sees canonical features and bounded excerpts. CoT can raise suspicion but cannot independently clear an input or authorize an action.

### Layer E: selective counterfactual replay

Only disagreement/high-risk cases trigger counterfactual variants, such as removing or attenuating suspicious spans while holding the trusted task and tool schema constant. Compare action trajectories. A dangerous action that disappears when untrusted control signals are weakened is evidence of causal influence.

### Layer F: deterministic evidence reducer

The reducer combines typed evidence according to a versioned policy. Examples:

- deterministic high-severity signal -> `Injection`;
- hard behavioral tripwire -> `Injection`;
- multiple independent semantic views agree -> calibrated verdict;
- major disagreement -> `Suspicious` and optional escalation;
- unsupported language -> `UnsupportedLanguage`;
- malformed/oversized input -> `InvalidInput`.

No final LLM is permitted to override a deterministic hard failure.

## 6. Firewall defense layers

1. Validate schema and canonicalize arguments.
2. Check declared capabilities and hard deny unauthorized tools/scopes.
3. Classify side-effect severity deterministically where possible.
4. Run independent semantic checks for task alignment, privilege, destination trust, and data flow.
5. Reduce to `Allow`, `Deny`, or `RequireHumanApproval`.
6. Bind approval to the exact canonical proposal and relevant object versions.
7. Execute through a registered capability-scoped tool with an idempotency key.
8. Verify postcondition and record the side-effect ledger.

The Firewall must not receive raw attacker content. It receives the trusted goal, canonical proposal, provenance classes, and minimal evidence needed for alignment.

## 7. Secure Issue Planner policy

Recommended default for unattended private/personal operation:

```toml
mode = "allowlist"
untrusted_action = "ignore"
```

Recommended reference-example mode:

```toml
mode = "hybrid"
untrusted_action = "ignore"
```

In hybrid mode, allowlisted content enters directly; other content must pass the Sentinel. Comments are assessed individually. A non-allowlisted body or comment rejected by policy is never forwarded into planning context.

Automatic close is optional and disabled by default. A close proposal must pass Firewall and normally HITL. Tests use a fake GitHub service and synthetic repositories before any live mutation profile is enabled.

## 8. Security invariants

The implementation is unacceptable unless all are true:

- the Sentinel probe cannot reach a real tool backend;
- synthetic honeytokens cannot be confused with production credentials;
- unsupported language cannot be mapped to `Clean`;
- a trusted issue author does not confer trust on third-party comments;
- untrusted content rejected by allowlist is not fetched into LLM context;
- raw malicious text/CoT is not forwarded to the trajectory observer by default;
- no model verdict overrides a deterministic capability or policy denial;
- no repository mutation occurs without Firewall decision and required approval;
- crash/retry/replay cannot duplicate committed side effects;
- cache reuse is invalidated by security-relevant policy/schema/model changes;
- cross-trust-domain KV reuse is disabled by salt/serving isolation;
- ordinary logs do not expose real secrets, synthetic credentials, or unrestricted CoT;
- the adversarial acceptance suite records zero unauthorized issue mutations.
