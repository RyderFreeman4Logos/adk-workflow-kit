# ADR-0024: Do not create a companion recipes repository

- Status: Accepted
- Date: 2026-08-29
- Source: Issue #187

## Decision

No companion repository is created for M2-02. The core checkout remains a
workspace and is not itself a path-independent package. The supported
boundary is the public crate set consumed directly from one exact Git
revision:

- the root `Cargo.toml` remains a workspace manifest, not a published crate;
- `workflowctl` and internal workspace tests may continue to use sibling
  `path` dependencies;
- downstream consumers use the public `workflow-compiler`, `workflow-adk`,
  `workflow-testkit`, and `workflow-runtime` crates, all pinned to the same exact
  revision.

Keep the executable recipes and decision evidence in this repository. Do not
create a companion GitHub repository. Downstream consumption uses a
published crate or an exact git revision pin. The tracked #269 consumer
template and `just issue-269-acceptance` entrypoint provide the reproducible
downstream boundary proof and exercise `run/resume/inspect/replay` using
local-only gates.

## Future creation gate

If the prerequisites become true, a follow-up decision must verify the
following before creating anything:

- pin `adk-rust = "=2.1.0"` exactly;
- keep ADK implementation types out of project contracts;
- do not fork ADK internals; file core defects in this repository;
- do not add hosted CI or GitHub Actions;
- retain executable downstream evidence for the four dogfood commands and
  local-only gates.

## Consequence

The no-create decision avoids a second package/release surface while the
workspace still relies on internal path dependencies. The existing workspace
and its local hooks remain the source of truth; reconsider only after a
published-or-pinned consumer boundary and downstream evidence exist.

## #269 acceptance boundary

The external consumer at `/home/obj/project/downstream/adk-workflow-kit-269`
uses no workspace or path dependency. Its four direct public dependencies
pin the same revision
`026b883a58bab6cc2d0c8610b44e3983e6017cb8`. The consumer-owned fixture wires a
fake offline profile, prompt, Skill, connector, and data through the public
APIs and runs exactly these operations:

1. `validate` via `workflow_compiler::compile_file`;
2. `lock` via `WorkflowLock::try_from_plan` and `to_toml`;
3. `run` via `ExecutionBackend::run`;
4. `inspect` via `ExecutionBackend::inspect`;
5. `resume` via `ExecutionBackend::resume`, preserving identity without a
   duplicate connector effect;
6. `replay` via `ReplayBundle`, structural-only and without execution.

The tracked template under `examples/02-downstream-consumer-269` and the
`issue-269-acceptance` recipe reproduce the proof. Cargo output uses the
consumer's lexical `target` symlink and no provider credentials or endpoints.

Clean start (the selected directory need not exist):

```sh
ISSUE_269_DOWNSTREAM="$HOME/project/downstream/adk-269-clean" \
ISSUE_269_TMPDIR="$HOME/tmp" just issue-269-acceptance
```

The entrypoint copies missing template files, retains the generated consumer
`Cargo.lock`, prepares `/ssd/mirror-rootfs<absolute-consumer-root>/target`, and
prepares the explicit runtime temporary base (physical path at most 48 bytes).
Defaults are `$HOME/project/downstream/adk-workflow-kit-269` and `$HOME/tmp`;
semantic controls preserve both selections for every child operation, and
Just passes selected paths literally rather than evaluating shell expressions.
It refuses stale or linked owned files and never overwrites unknown user
state. `--prepare` on the Python entrypoint performs setup/identity checks
without building. Ordinary acceptance uses `--locked`, not lock regeneration.
To update a previously prepared consumer, use a new empty external directory
or explicitly reconcile its owned files first. Every source, manifest, lock,
and asset digest is checked before and after execution and included in the
receipt. `_quality-gates` invokes both the bootstrap controls and acceptance;
workspace-only compilation is not evidence for the external executable.

The root workflow binds `assets/prompt.txt` through the public hashed agent
instruction contract. Data is serialized into an actual connector request;
the fake model activates the Skill, discovers its resource from the activation
response, and forwards the read bytes and digest into that same request.
Typed tool events and the exact `EffectKey`/`EffectJournal` result demonstrate
that those external bytes reached the tool route, not just profile storage.

The proof compares all inspect fields and all stable resume fields, including
artifact and plan identity, with the expected resume-count increment. It reads
the exact terminal artifact through `FilesystemArtifactStore`, verifies its
content digest and terminal marker, and verifies the expected model answer in
typed durable events. The terminal artifact is a terminal marker, not the agent
answer; the two observations are deliberately distinct. Model/tool event
records and the single committed connector result remain unchanged on resume.
Run roots are retained as small durable evidence, not recursively chmod/deleted.
In the prepared consumer, recheck with
`ISSUE_269_TMPDIR=<same absolute prepared run base> just verify <run-id>`.
Use the parent directory of the receipt's `run_root` as that base (quote paths
as needed); preparation does not export it into the caller's shell. Verification
performs inspect/resume and increments `resume_count`; it is not read-only.
`just issue-269-semantics-test` also corrupts and restores only its own generated
artifact, artifact reference, output events, and effect row as negative controls.
The canonical local gate includes these controls; replay remains structural-only.
